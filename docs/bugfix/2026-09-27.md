# 1. 已经显示最新消息，重进会话却先退回旧消息

**出现情况 / Case**

- 手机已经显示提问和最新回复，离开再进入却显示上一版内容；网络恢复后才可能追上。
- 更容易触发的顺序：收到实时回复 → 最终 HTTP 快照尚未返回 → 切换会话或退到后台 → 再打开。断网时会一直停留在旧缓存。
- 另一路径：加载过更早历史，随后刷新最新 12 轮；旧实现保存的是原始最新页，而不是已经合并的完整已加载历史。

**原因**

缓存原本存在，但只保存 `ThreadDetail`，没有保存 `liveMessages`、轮次映射和服务器已确认发送的临时气泡。切换时会清空这些内存状态。详情和索引还分别交给独立的 detached Task 写盘；atomic 写文件只能避免半个文件，不能保证较新的任务最后完成。前台恢复又直接跳过已完成的会话，因此可能不再核对最后一段内容。

这是代码路径和模拟回归确认的问题；没有读取用户手机的旧缓存，不能断言某次实际出现只由其中一个原因触发。

**修复 / Patch**

- `apps/ios-native/CloudexNative/LocalConversationCache.swift`：`CachedThreadDetail` 同时保存快照、实时消息、消息所属轮次、运行状态及已确认发送的气泡。`saveThread` 在调用顺序上直接进入一个串行磁盘队列，编码和 compact 在队列内完成；读取等待先前写入，`flush` 提供后台保存结束点。
- `apps/ios-native/CloudexNative/AppViewModel.swift`：`checkpointConversation` 保存当前已合并的数据，不再保存原始最新页；实时渲染后的保存按 1 秒节流，切换会话、创建新会话、切换主机、终态事件和进入后台立即提交保存。后台通过原生 background task 给磁盘队列完成的时间。
- `openThread` 在清理旧页面前保存，加载后通过 `restoreConversation` 恢复实时内容，再核对网络快照。消息索引从同一份详情重建，取消第二份可能错版的索引文件写入。
- `resumeFromForeground` 也刷新已完成的会话。`loadOlderTurns` 保留当前线程元信息，避免旧分页响应回退状态；保存已加载历史及最早分页游标。
- `apps/ios-native/CloudexNative/Models.swift`：消息和附件支持 Codable，但不序列化 Markdown 解析对象；只恢复明确标记 `sent` 的待入库气泡，不能把 `sending` 冒充成功。

**缓存格式与边界**

新缓存键使用主机 profile ID + thread ID，LAN/VPS 地址切换仍可复用同一主机的数据，不同主机隔离。旧格式没有主机归属，因此不盲目迁移；升级后第一次打开会话需要联网建立新缓存，服务器历史不会被删除。缓存位于 iOS 的 Caches 目录，可被系统清理，不是消息备份。正常进入后台会提交并等待写盘；突然崩溃或断电仍可能丢失最近一个保存间隔内尚未落盘的内容。

**验证**

`apps/ios-native/CloudexUITests.swift::testConversationCacheSurvivesReopenAndStaleSnapshots` 调用 DEBUG simulator 的 `runCacheRegression`。测试使用隔离临时目录、真实磁盘队列和实际 `openThread`/渲染路径，只替换 HTTP 页数据；不会创建真实 Codex 会话。覆盖即时离开重进、离线恢复、重新实例化 cache/model 从磁盘读取、附件/发送状态恢复、跨主机隔离、30 次大小不同的顺序写入、旧 HTTP 版本、历史/游标保留、后台 flush 以及已完成会话前台刷新。临时目录测试结束后移除。

# 2. 旧网络快照和断线重放覆盖已显示的实时回复

**出现情况 / Case**

- SSE 已显示“最新回复：已经显示”，HTTP 只返回同一 item ID 的“最新回复：”。旧逻辑仅凭 ID 就删除实时内容，较短文本覆盖较长文本。
- 新一轮的实时回复到了，但 HTTP 详情还只有上一轮；旧渲染路径只在整个 turns 为空时补上无归属的实时消息，因此这轮内容可能暂时不见。
- 重连从 `item/started` 重放，空文本或短前缀覆盖恢复的气泡；服务端只保留 250 条事件，重放也可能从消息中间的 delta 开始。
- HTTP 已确认一部分文本后，下一条 delta 若从空字符串开始拼接，会把前面内容丢掉。

**修复 / Patch**

- `AppViewModel.swift::removePersistedLiveMessages`：同一个 ID 或 completed 状态不再代表文本已追平。仅较短旧前缀不会清除实时内容；一致内容、扩展内容或不同的修订内容才接管。
- `buildMessages`：同 ID 的实时内容覆盖较旧详情，HTTP 尚未包含的新轮次也显示。已经完成的轮次中，commentary 仍放在过程区域，final_answer 保持回复气泡；phase 随缓存保存。
- `beginLiveMessage` / `appendLiveDelta`：重放单独累计，不把重放前缀追加到恢复内容上；没有 item 起点的重放尾部不直接覆盖完整消息，重放结束补拉快照。正常 delta 接着已经确认的详情文本累计。
- `mergingLatestPage`：拒绝明确较旧的 updatedAt；相同版本的短前缀、completed → running 回退受保护。保留当前轮次顺序及已加载历史，同时允许完成后真正的新修订替换正文，不再永远沿用完整旧 turn。
- `openThread`、分页/详情请求、SSE 回调和终态重试绑定页面 generation，避免旧页面的异步结果写回重新打开的页面；终态重试核对实际 turn ID。

**Codex 机制与升级索引**

在上述版本基线下，Cloudex 消费 app-server 的 `turn/started`、`item/started`、`item/agentMessage/delta`、`item/completed` 和终态通知；HTTP compact 页与事件可能不同步。`turn/completed` 不保证 Cloudex 下一次读到的持久化文本已经完整。250 条重放上限及 `replay-complete` 是 Cloudex 服务端自身的实现，不是 Codex 官方协议承诺。

升级后核对 item/turn ID 稳定性、phase 的 `commentary`/`final_answer`、进行中状态拼写、updatedAt 单位及单调性、compact 页的 itemsView/detailsLoaded 和 before 游标。若这些语义改变，应调整对应合并路径并运行本文件的回归，不能只凭版本号认为兼容。缓存自身的 savedAt 只记录保存时间，不冒充服务端修订号。

**验证与交付记录**

# 3. compact 过程入口排在最终回答之后，展开时移动或消失

**Case**：读取到的 5 份手机缓存中，39 轮的过程入口没有时间戳，但最终回答有时间戳。原全局时间排序把入口移到回答后面；详情回来后时间补齐，入口又跳回前面。这里补充的是本轮实际缓存审计，区别于第 1 项当时尚未读取手机缓存的证据范围。

**Patch**：`AppViewModel.buildMessages` 按轮次建立用户消息 → 过程摘要 → 最终回答的语义顺序，取消跨轮时间排序；摘要 ID 固定为 turn ID 派生值。`loadTurnDetails` 保留 compact 的过程计数，空详情不删除摘要。`ContentView.ProcessSummaryBubble` 显示加载错误/重试/暂无过程详情，展开状态存入模型而非 cell。`NativeChatList` 用稳定 ID 复用，原始时间只用于显示。

**回归**：36 轮混合时间戳和缺失过程时间的 compact 数据；详情首次失败、第二次成功及空详情的 UI 测试。用户看到的入口和最终回答分别使用独立辅助功能标识，避免父视图标识覆盖可点击按钮。

# 4. 首次打开连续多轮刷新，迟到缓存可能覆盖或丢失最新内容

**Case**：缓存准备、HTTP、SSE 重放和 Markdown 完成时间不同；先清空再分批显示、重复定位，会让页面像多次加载。网络先到时还可能先覆盖磁盘缓存，使尚未读取的旧历史只剩最新 12 轮。

**Patch**：`ConversationLoadState` 区分 loading/ready/syncing/failed。`openThread` 并行读取缓存和 HTTP，缓存只准备最近 12 轮，其余存入 `cachedOlderTurns`；当前有效快照准备完成后才进入可显示状态。网络先到后拒绝迟到缓存覆盖最新详情，但保留旧历史和未确认的实时覆盖层。`initialCacheLoadGeneration` 阻止磁盘尚未读取时写掉缓存。后台更新不重新进入首次加载状态。Markdown 保留解析复用与 epoch 校验，折叠过程不提前解析。

**回归**：真实磁盘队列，缓存先到/网络先到、离线、36→12 轮首屏、手动分页、SSE 旧前缀重放，以及首次内容出现后不再发布空列表。HTTP 失败且无缓存时显示重试入口。

# 5. 滚动白页、底部空白和分页时阅读位置跳变

**Case**：旧聊天区同时有 ScrollViewReader、默认底部锚点、UIKit offset 回写和多套延时补滚。首页行出现还能触发历史分页；历史 prepend 在手势中完成时，原阅读锚点被后续滚动事件覆盖。

**Patch**：新增 `NativeChatList.swift`，采用 UICollectionView、diffable data source 和 UIHostingConfiguration。单一 coordinator 负责首次定位、跟随底部、目标消息跳转和 ID + 相对位置锚点。拖动/减速期间暂存结构更新，手势结束捕获当前锚点再应用；用户接近顶部才请求历史。删除原透明隐藏、0.6 秒等待、估算高度及多套延迟补滚逻辑。内容变化只 reconfigure 改变的行，展开状态独立保存。附件固定高度占位，避免下载后突然长高。

**验收边界**：快速交替滑动用例在每次动作后、任何补救手势之前保存截图并检查标题、输入区、消息区域。整页白屏的单一根因未被实际捕获，因此不能用原生列表改造或构建成功宣称真机白屏已彻底解决。实际 iPhone 14 Pro / iOS 27.0（24A437）的滚动、键盘、前后台验收仍须有设备连接后的证据。

# 6. 刷新阻塞发送、切换后迟到发送结果影响另一会话

**Case**：原刷新与发送共用 busy；旧请求返回可能清掉新页面的附件或草稿。新建会话超时后没有 thread ID/SSE，却保持 running，会导致后续消息只能进入无法执行的队列。旧主机慢刷新也可能阻止新主机刷新。

**Patch**：`isRefreshing` 与发送状态分离，刷新按 connection generation 合并。`submitPrompt` 绑定连接、会话 generation、请求 UUID 和附件快照；旧回调不得清理新页面状态，steer 成功不再清普通草稿。超时显示未确认、不自动重发；无会话 ID 时恢复已知运行状态。`stop` 不再复用发送状态。切换主机异步读完缓存后再次核对主机身份。

**回归**：`runCacheRegression` 替换传输结果、执行真实 submit 回调，覆盖刷新中乐观发送、发送中切换、迟到超时不能覆盖新草稿/错误、无 ID 超时的未确认状态。无真实 Codex 测试会话。

# 7. 搜索旧消息时覆盖最新缓存，以及后台重复刷新

**Case**：around 页直接替换当前详情会让缓存退到历史页；旧页中发送后，最新结果可能留在不可见窗口。主页订阅完整模型，又随每批流式文字重算列表。

**Patch**：缓存内目标直接按需展开历史；远端 around 搜索保存 `searchReturnDetail`，持久化继续使用保留的最新窗口。点最新/发送前恢复最新窗口；后台快照仍更新运行状态和去重。`HomeUpdates` 只订阅主页相关数据，项目筛选/排序仅在相关输入变化时重新计算。项目缓存异步读，相同健康/审批/概览不重复发布；会话缓存仅保存实际改变的快照。文件与审阅子页首次选中才创建，代码预览复用高亮与行数/宽度测量。

# 8. 全应用视觉不统一、硬蓝边框与深色发送按钮可辨性不足

**Case**：首页、气泡、过程和设置采用不同颜色/圆角；输入区出现硬蓝框，发送按钮固定黑底白字在深色中不够清楚。用户选择“原生玻璃感”的综合美化方向。

# 10. 手机不能选择真正的 Codex 计划模式

**Case**：模型和推理强度可选，但不能发起 Plan 轮次。访问权限（只读、工作区、完全访问）与协作模式不是一回事；在提示词里写“先计划”不能替代协议模式。

**Patch**：`server/src/codex-client.js` 初始化声明 `experimentalApi`；`collaboration-mode.js` 根据真实 `collaborationMode/list` 返回值组装 `turn/start.collaborationMode`。新增 `/api/collaboration-modes`，新建、继续、分叉及队列共用模式参数。模式设置包含 model、reasoning_effort、`developer_instructions: null`，保留 Codex 内置指令。参数校验在申请 writer/创建会话前执行，非 Codex provider 不接受 Codex 模式。

`AppViewModel.swift` 按主机和会话记住选择，切换会话立即隔离旧模式。`ContentView.swift` 在模型菜单增加普通执行/计划模式；“按此计划执行”切回普通模式并填入草稿，由用户发送。能力读取失败时，已选 Plan 明确阻止发送，不悄悄降级。UI 测试发现模式已变而底部按钮不刷新，根因为原生列表 footer 的内容签名漏掉 `collaborationMode`，已加入签名，局部刷新该行。

**版本基线与升级索引**：当前受管 CLI `0.157.1`，Desktop bundled CLI `0.155.0-alpha.16.4`。本次用本机 CLI 导出的 JSON Schema 核对 `CollaborationModeMask` 与 `CollaborationMode`，二者不能混用。升级时复核实验 API 开关、list 返回的 mode/model、settings 必填字段以及 `turn/start` 模式覆盖外层 model/effort 的行为。当前仅提供服务端真实返回且已实现的 default/plan，不凭名称虚构其他模式。

# 11. “查看实际界面截图”等链接无法打开，过程与生成图片无法浏览

**Case**：Markdown 链接被吞掉；UICollectionView 的 UIHostingConfiguration 没有自动继承外层 SwiftUI 的预览环境。旧代码还在不同页面重复下载/预览，并用文件名猜路径。工具生成的图片可能只有协议附件，没有最终文本中的图片链接。

**Patch**：新增 `ios-native/CloudexNative/FilePreview.swift`，统一聊天和 `WorkspaceTabsView.swift` 的文件预览。每个原生列表 cell 显式注入 API client、项目根目录和 openURL；支持本地绝对路径、相对路径、file/sandbox 链接、中文与空格、源文件 `:line` 后缀。每次预览绑定来源主机，切换主机不挪用另一台主机的认证。HTTP(S) 普通网页仍走系统浏览器，明确的图片地址可内置查看。

`MarkdownRendering.swift` 为段落中的图片生成固定尺寸缩略图；附件和折叠过程中的图片也可点击。`media-attachments.js` 统一 imageView.path、imageGeneration.savedPath/saved_path 和 MCP 类型明确的 image 内容；CLI 历史、API 历史、实时事件、compact 页及 Swift TurnItem 保留附件。稳定的 `-images` ID 避免加载历史后再出现同一条工具图片。没有把不透明 imageGeneration.result 或任意工具文本猜成文件路径。

内置渲染范围：图片/放大、GIF 播放与暂停、Markdown 渲染与相对链接、HTML/SVG、QuickLook 支持的 PPT/PPTX/PDF，以及原有代码预览；提供源码切换、分享和失败重试。预览关闭清理本次 UUID 临时目录。Office 预览使用 iOS QuickLook，不能承诺 PowerPoint 动画、字体和复杂版式完全一致；旧 `.ppt` 走同一系统路径，本次实际点击使用 `.pptx`。Markdown 复用现有解析器，暂不声称覆盖所有 CommonMark 图片嵌套写法。

**安全与实际失败 Case**：`server.js/sendFilePreview` 同时验证逻辑路径和 realpath，阻止符号链接绕过文件范围；统一根目录与目标的 realpath，修复 macOS `/var` 与 `/private/var` 别名导致合法文件 403。HTML 用独立的 `cloudex-preview` scheme、无持久化 WebView、默认关闭脚本；手动开启脚本也不授予 token、原生桥接、网络请求或文档目录外的资源访问。导航失败显示错误/重试，不留空页。中文 HTML 未声明编码时实测乱码，已对文本资源添加 UTF-8 响应头。文件最大 50 MB，外部图片请求不携带 Cloudex token。

**版本机制**：针对上述 Codex 基线的类型化 image/MCP 字段；Codex 升级后重新核对生成图片保存位置、MCP content 格式及 live/history item ID 的一致性。文件预览本身不依赖 Codex writer，也不靠启动测试会话生成文件。

# 12. 等待发送把多条消息合并，关掉手机后队列不能可靠执行

**Case**：旧 pendingSteerDraft 是合并文本，不能独立保存三条消息的附件、模式、顺序和状态。只依赖手机调度时，杀掉 App 就失去续发能力；网络超时直接重发可能执行同一任务两次。

**Patch**：新增 `server/src/message-queue.js`，每个会话独立 FIFO worker，串行原子 JSON journal（临时文件后 rename，0600），先记录 dispatching 再请求 Codex。稳定客户端消息 ID 保证重试不重复执行；每项保存消息、附件、model、effort、模式和访问权限快照。正在运行的 turn ID 精确匹配终态；SSE 丢失时定期读历史补核对。后台服务器继续调度，不要求手机保持连接。

`server.js` 新增每会话 queue GET/POST 和 queue/changed SSE，复用普通发送函数；已有队列时普通发送不能插队。暂停、继续、上移、修改和取消限于可操作状态；停止/归档先暂停队列。writer 冲突停在 blocked，用户解除占用后继续，不抢占 Desktop。发送超时或 dispatching 期间服务器重启进入 unconfirmed 并暂停，要求核对，绝不自动重发。取消未确认上传也写入服务器 tombstone，迟到的相同 ID 不能再入队。

`AppViewModel.swift` 使用主机/会话隔离的本地 outbox，点击后立即显示独立待上传项；确认前保留载荷，SSE/HTTP 按 revision 合并。迟到回调不能清理另一会话草稿/队列。旧合并草稿保留手动恢复，取消旧自动续发。`ContentView.swift` 显示独立消息状态与菜单，忙碌时点发送入队，长按可补充当前任务。新会话尚未取得 ID 时明确提示稍后入队并保留输入，不再无声忽略；无运行任务且输入为空时不显示错误的停止按钮。

**边界与升级索引**：未确认发送暂不依据相似文本猜测是否成功，需要用户核对后停止追踪；已完成/已取消的 ID 保留用于幂等。单会话最多 100 条未结束队列项，journal 暂无自动压缩。队列依赖上述 Codex 基线的 turn/start、clientUserMessageId 和稳定 turn ID/终态；升级时重点验证超时、终态到达早于 HTTP 返回、断线重连、writer 冲突及 Windows fallback 的 turn ID。服务端不绕过 Codex 对其他客户端的 writer 限制。
