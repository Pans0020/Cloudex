**Codex 基线**：本机 `codex --version` 返回 `codex-cli 0.157.0`。以下“Codex 机制”是该版本在本机文件及 Cloudex 交互中的观察结果，不应当作未来版本的稳定协议。

**升级索引**：升级 Codex 后先核对三件事，再验证手机端：

1. `~/.codex/sessions` 是否仍使用 `rollout-...-<thread-id>.jsonl`，续写是否仍使用 `rollout-...-<thread-id>_<continuation-id>.jsonl`；检查 `session_meta.payload.id` 与文件名中的原任务 ID 是否一致。不要用文件名末尾的 UUID 当作任务 ID。
2. `app-server` 的 `thread/resume`、`thread/unsubscribe`、`thread/started` 与 `turn/start` 是否仍有相同的 writer/订阅语义。尤其不能从收到 `thread/started` 推断 Cloudex 拥有 writer，也不能为了只读浏览主动 resume。
3. 运行 `npm test`，再分别通过本机与手机实际使用的转发地址检查 `/api/projects`、`/api/threads/:id?limit=12`、`before` 分页和 `/message-index`；用一条桌面续写的任务确认手机能看到用户消息与最终回复。SSE 关闭/租约还需用真机和代理链路检查。

# 1. 多台主机缺少统一任务概览

- **出现情况 / Case**：保存了多台 PC 或服务器后，手机要逐台切换才能知道哪台在线、有哪些运行任务或待审批请求；同名项目也难以分清属于哪台主机。这是当天提出的移动端能力缺口，不是 Codex CLI 回归。
- **修复**：增加保存的主机 profile、主机概览与切换入口。`apps/ios-native/CloudexNative/AppViewModel.swift:1213` 管理 profile，`:1490` 拉取概览；`apps/ios-native/CloudexNative/SidebarView.swift:370` 展示各主机状态和项目。
- **验证 / 提交**：随 `6228d85` 实现并完成 iOS 构建/安装；之后的并发加速见第 8 项。此能力的最终真机视觉验收不在服务端单测范围内。

# 2. 手机内容进入任务的路径不完整

- **出现情况 / Case**：手机里的照片、截图、网页或文字不能方便地从系统分享菜单选主机和会话后作为可编辑草稿使用；语音输入和快速查看最近任务也缺入口。这同样是产品能力缺口，不属于 Codex 文件格式问题。
- **修复**：分享扩展写入 App Group 收件箱，由 `apps/ios-native/CloudexShare/ShareViewController.swift:4` 接收，`apps/ios-native/CloudexNative/SidebarView.swift:1092` 选目标；`apps/ios-native/CloudexNative/AppViewModel.swift:1287` 处理分享项，`:2149` 上传手机图片；`apps/server/src/server.js:1311` 校验并保存图片。`apps/ios-native/CloudexNative/SpeechInputController.swift:5` 负责语音转写，`apps/ios-native/CloudexWidget/CloudexCurrentTaskWidget.swift:56` 展示最近一次同步的任务快照。
- **验证 / 提交**：`6228d85`；服务端图片格式/大小边界由 `apps/server/test/upload-image.test.js` 覆盖。小组件是最近一次同步快照，不承诺后台实时状态。

# 3. 手机关闭后，电脑会话仍被 Cloudex 占用

- **出现情况 / Case**：手机 App 已关闭，Codex Desktop 的同一任务仍暂时无法继续对话；点“重试”在占用释放前无效。手机连接结束不等于 Cloudex 对 Codex 的订阅已释放。
- **原因与 Codex 机制**：在本机 `0.157.0` 的控制链路里，Cloudex 对任务执行 `thread/resume` 后需要显式 `thread/unsubscribe`。仅断开手机 SSE 而保留 app-server 订阅，会让 Desktop 继续遇到 writer 占用。
- **修复**：iOS 进入后台时停止全局和任务 SSE，见 `apps/ios-native/CloudexNative/AppViewModel.swift:1174`；服务端最后一个任务 SSE 关闭后延迟 250 ms 释放订阅，见 `apps/server/src/server.js:558`；`apps/server/src/codex-client.js:343`、`:358` 串行处理 resume/unsubscribe，避免刚重连就误释放；发消息、新建或 fork 后也在 `finally` 安排释放。
- **验证 / 提交**：`6228d85`；`apps/server/test/turn-lifecycle.test.js:91`、`:104`、`:120` 覆盖释放、快速重连与竞态。用户随后确认 Desktop 能再次输入。

# 4. 强退或代理未及时关闭 SSE，释放仍可能拖很久

- **出现情况 / Case**：手机实际已离开任务，但通过 VPS/反向代理的长连接未及时触发服务端 `close`，第 3 项的“最后一个 SSE 关闭”条件迟迟不成立。
- **修复**：新版 iOS 在前台选中任务时约每 5 秒调用 `/api/threads/:id/lease`，见 `apps/ios-native/CloudexNative/AppViewModel.swift:1470`；服务端在约 20 秒无续租后销毁静默 SSE 并安排 unsubscribe，见 `apps/server/src/server.js:571`、`:1426`。这给异常断线增加了有界的回收路径，不依赖 TCP 立即通知。
- **验证 / 提交**：`ee246ea`；`apps/server/test/stream-lease.test.js:6` 验证续租可延长连接、停止续租后连接会关闭。20 秒是服务端租约值，不是保证 Desktop 在所有网络条件下恰好 20 秒恢复。

# 5. 租约初版会误断开旧版 iOS 客户端

- **出现情况 / Case**：第 4 项的初版曾给所有任务 SSE 启用 20 秒超时；尚未升级、不会发送 lease 的旧版 App 会被周期性断开。
- **修复**：只有显式使用 `?lease=1` 打开的新客户端才启用租约计时；旧客户端保持原有 SSE 行为。入口在 `apps/ios-native/CloudexNative/AppViewModel.swift:2371`，服务端判断在 `apps/server/src/server.js:583`、`:1439`。
- **验证 / 提交**：`a93a7f5`；租约单测改为显式选择 leased 连接。旧版客户端未在真机上做单独端到端测试，因此“旧版完全兼容”仍以代码路径核对为依据。

# 6. 未在电脑打开的任务仍提示 active writer

- **出现情况 / Case**：手机发送消息时出现 `thread ... already has an active writer`，即使用户并未在 Codex Desktop 打开该对话。打开手机会话本身不应抢占 Codex writer。
- **原因与 Codex 机制**：先前 Cloudex 为只读 SSE 调用了 `thread/resume`，还把收到的 `thread/started` 通知误当成自己已订阅。通知描述任务事件，不证明 writer 所有权。
- **修复**：只读任务 SSE 只返回 `read-only`，不 resume；仅发送 turn 时 resume。删除 `thread/started` 对 `subscribedThreads` 的错误赋值；真正冲突转为明确的 HTTP 409，而不是原始 502。位置：`apps/server/src/server.js:1457`、`:1590`、`:328`，`apps/server/src/codex-client.js:304`。
- **验证 / 提交**：`769a0da`；`apps/server/test/passive-thread-stream.test.js:19`、`:35` 和 `apps/server/test/turn-lifecycle.test.js:85` 覆盖只读浏览、409 与错误所有权记录。

# 7. 打开已有会话时，本地缓存被模型请求挡住

- **出现情况 / Case**：手机已有会话缓存，但点开仍先显示“正在打开对话”，尤其经 VPS 时会等模型接口往返；即使缓存已到手，远端刷新也可能被已锁定的静态布局挡住。
- **修复**：模型列表只在需要时后台加载，不再每次强制请求；本地详情和消息索引加载后即可解除打开状态，网络详情随后覆盖缓存；详情变化时刷新已完成会话的内容快照。位置：`apps/ios-native/CloudexNative/AppViewModel.swift:1585`、`:1643`，`apps/ios-native/CloudexNative/ContentView.swift:310`。
- **验证 / 提交**：`3beb396`；iOS 模拟器及真机构建通过，新版已安装到 iPhone。没有自动化真机首屏计时，速度收益属于调用链改进，不宣称固定毫秒数。

# 8. 首页及多主机概览串行网络等待

- **出现情况 / Case**：`refresh()` 先请求 health，再依次请求项目和审批；多主机概览又逐台依次执行 health、项目、审批。VPS 每次往返会叠加为明显等待。
- **修复**：项目接口直接承担连通性判断，项目和审批并发；各主机概览使用 task group 并发拉取，单台主机仍保留局域网/Tailscale 候选地址回退。位置：`apps/ios-native/CloudexNative/AppViewModel.swift:1380`、`:1490`、`:1506`。
- **验证 / 提交**：`3beb396`；iOS 模拟器和真机构建通过。本机 API 与 VPS 往返曾分别测量；这里不把单次网络样本当成稳定性能承诺。

# 9. 超长 Codex 会话每次读取都重新解析 JSONL

- **出现情况 / Case**：服务端读取最新 12 个回合时，原先仍会读取并解析整份 JSONL；长任务频繁刷新会重复做同样工作。
- **修复**：`apps/server/src/cli-sessions.js:724` 串行化详情读取，`:732` 从上次完整行的字节偏移读取新增内容，`:773` 用文件身份、大小与修改时间决定能否复用解析状态。第 10 项后来把同一缓存扩展到一组续写文件。截断、同长度改写和文件替换会重新解析；同一 inode 上“改写成更长文件”仍按 Codex 追加写入处理，是当前明确边界。
- **验证 / 提交**：`3beb396`、`40e7ea4`；`apps/server/test/turn-lifecycle.test.js:9` 覆盖追加、半行和重写。一次 10 MB 本地样本首次解析约 53 ms，原文件未变化时二次读取低于 1 ms；首次读取仍需完整解析。

# 10. “阅读JH”续写回合在手机上消失

- **出现情况 / Case**：手机发送“今天是什么5层运”后收到完成通知，但会话页看不到提问或回复；Desktop 两条都可见。修复前 Cloudex 详情 API 只返回到较早的一条七月时间追问。
- **原因与 Codex 机制**：本机 `0.157.0` 把后续回合写进 `rollout-...-<thread-id>_<continuation-id>.jsonl`；`session_meta.payload.id` 仍是原任务 ID，续写文件只含后半段。旧正则只接受末尾直接为 `<thread-id>.jsonl` 的文件，导致整个续写文件被 `findSessionFiles()` 忽略。完成通知来自实时事件，而历史页走文件读取，所以两者可不一致。本机检查到 16 个这类文件，首条元数据中的 ID 均与原任务 ID 一致。
- **修复**：`apps/server/src/cli-sessions.js:8` 识别可选的续写 ID，`:700` 返回原任务 ID，`:884` 按原 ID 分组，`:760` 用同一解析状态依时间顺序合并所有片段，`:902` 读取整组详情，保留分页、归档、去重和追加缓存。`apps/server/src/windows-cli.js:328` 排除续写文件作为“新任务”，避免误认其他任务的续写。
- **验证 / 提交**：`40e7ea4`；`apps/server/test/cli-continuation.test.js:13` 覆盖跨文件合并、追加与归档；最终服务端 28 项测试通过。真实任务恢复为 14 个回合，项目列表仅一条；本机及 VPS 转发的详情 API 均返回最新提问和最终回复，`before` 分页无重叠，消息索引也包含两条。Mac 上服务已重启；该提交只改服务端，手机无需重装。最终手机屏幕没有自动截图验收，重新进入会话后应由 App 拉取新详情。

# 11. 手机点击发送后几秒才出现自己的消息，等待状态只有转圈

- **出现情况 / Case**：在已有会话或新建会话点击发送，右侧用户消息要等 HTTP 请求返回、会话详情再次加载后才出现；发送按钮和聊天底部都显示无说明的转圈，用户无法判断消息是否已提交或是否在等回复。
- **原因**：`submitPrompt()` 原先等服务端确认后才清空草稿，界面没有本地待发送消息；聊天底部的 `ProgressView` 没有区分发送与执行阶段。若服务端开始执行后历史快照尚未写入，刷新也会延后消息出现。
- **修复**：`apps/ios-native/CloudexNative/AppViewModel.swift` 的 `submitPrompt()` 在请求前插入右侧临时用户消息并清空草稿，服务端确认后标记“已发送”，失败时恢复草稿；`buildMessages()` 按服务端 turn ID 和真实用户项去重，避免快照出现时双份消息。`apps/ios-native/CloudexNative/Models.swift` 只解码发送所需的 turn ID。`apps/ios-native/CloudexNative/ContentView.swift` 显示“正在发送 / 等待回复”的文字状态并移除发送按钮、聊天底部的无说明转圈；临时项从快照消失时不再被滚动列表保留。
- **验证**：服务端 29 项测试通过，iOS 设备及 iPhone 18 Pro 模拟器 Debug 构建通过；模拟器成功安装并启动。模拟器没有配对服务器，因此未做端到端发送。iPhone 14 Pro 当前被 Xcode 标为 `unavailable`，尚未完成该版本的真机点按验收；即时回显及动画流畅度仍需连接真机复核。

# 12. 手机还开着会话时，Codex writer 可能长期占用；Desktop 只看会话也提示冲突

- **出现情况 / Case**：手机发送提示“此会话正由其他客户端占用”；电脑端未发送消息，仅打开会话。另一方向上，手机保持 SSE 连接时，Cloudex 自己也可能在任务已结束后继续持有 writer，使电脑无法立刻接手。
- **原因与 Codex 机制**：在本机 `codex-cli 0.157.0` 的 `thread/resume` / `thread/unsubscribe` 排他写入机制下，只读 SSE 不需要 writer；但服务端原先用“是否仍有手机 SSE 订阅者”决定是否调用 `thread/unsubscribe`，所以 SSE 长连接会阻止释放。Codex Desktop 自己持有 writer 的场景仍受上游排他规则限制，Cloudex 不能安全地强抢或并发写入同一会话。
- **修复**：`apps/server/src/server.js` 将 Cloudex 发起的回合记录在 `ownedRunningThreads`，在终止事件后安排 `thread/unsubscribe`，不再让手机只读 SSE 阻止释放；发送失败及无任务的新会话仍安排释放。409 文案提示电脑端仅打开会话也可能占用，并给出切换会话再重试的路径。`apps/server/test/passive-thread-stream.test.js` 覆盖 SSE 仍打开时执行释放。
- **验证**：服务端 29 项测试通过，含新增长连接释放用例；Mac LaunchAgent 已重启，服务监听 `8890`，认证后的健康检查返回 `200`。没有向用户真实会话注入测试消息，也未证明 Desktop 自身的 writer 能在保持该会话打开的同时共享；要并发写入同一会话仍需上游支持。
